# Conventions

Set by the walking skeleton (#21). Every later ticket follows them. Vocabulary: `GLOSSARY.md`; decisions: `docs/adr/`.

| `app/format.ts` | Shared display formats (dates, ordinals). |

## Adding a migration

1. Edit `app/db/schema.ts`.
2. `npm run db:generate -- --name <what_changed>` → `db/migrations/NNNN_<what_changed>.sql`. Read the SQL.
3. Commit the SQL **and** `db/migrations/meta/`. Never edit a migration that is on `main`; add a new one.
4. Tests pick it up automatically (`tests/support/setup.ts` applies all migrations to each test file's fresh D1). Deploys apply it before the new code goes live.

## Writing tests

Tests only go at the two seams from spec #20. A good test sets up inputs (rows, a recorded payload, a clock), calls a seam, and checks what a reader or the owner would see (or the stored rows/R2 objects). Never assert on internal helpers, query shapes or component structure.

### Seam 2: domain rules (`tests/domain/<rule>.test.ts`)

Table-driven with `it.each`, one row per case, a readable `name` per row, expected values written out by hand (from the spec, the glossary or a worked example), never computed the way the code computes them. Import from `~/domain` only. Pass `now` explicitly. Example: `tests/domain/time-display.test.ts`.

### Seam 1: the Worker surface (`tests/worker/<feature>.test.ts`)

Runs in workerd through `@cloudflare/vitest-plugin`, with a real local D1 (all migrations applied) and a real R2, isolated per test file.

- **Call an entry point** with `tests/support/worker.ts`: `get(path)` for pages, loaders and the iCal feed; `post(path, form)` for actions; `deliverIngestJobs(jobs)` for one batch to the queue consumer (returns acks and retries); `runIngest(jobs)` to run jobs plus every job they queue (fan-out, e.g. the roster seed) until drained, without touching the real local queue. Add a helper there for each new entry point (e.g. the scheduled handler).
- **Arrange state** with builders in `tests/support/seed.ts` (add one per entity as you need it).
- **Fix the clock** with `fixClock("2026-11-14T04:00:00.000Z")`. It fakes `Date` for the test and the Worker (same isolate). Production code reads time through `now()` from `~/clock` or `new Date()`, never via timers.
- **Stub outbound fetch** with `stubOutboundFetch([{ ...meta, body }])`. An unstubbed URL throws, so tests never hit the network.
- Both are reset after every test by `tests/support/setup.ts`.
- Examples: `tests/worker/athlete-page.test.ts` (page), `tests/worker/isu-speed-skating.test.ts` (queue + clock + fetch stub + R2 + health), `tests/worker/daily-ingest.test.ts` (cron).
- `runScheduled(cron, time)` and `runIngest(jobs)` capture whatever the Worker queues and return it; nothing reaches the real local queue. An action that queues through `env.INGEST` does use the real local queue: wait for its effect with `vi.waitFor` and give the test a longer timeout.
- Storage is shared by the tests in one file. When tests ingest overlapping data, start each from `clearIngestedData(env)` (`tests/support/seed.ts`).

### Recording fixtures for source raw copies

Adapters are tested against real federation payloads.

1. `npm run record-fixture -- world-athletics thiam-results.json "https://…"` writes `tests/fixtures/sources/world-athletics/thiam-results.json` (byte for byte) and `thiam-results.json.meta.json` (`url`, `status`, `contentType`, `recordedAt`).
2. In the test: `import body from "../fixtures/sources/<source>/<file>?raw"` and `import meta from "…/<file>.meta.json"`, then `stubOutboundFetch([{ ...meta, body }])`. Binary payloads (FIS ZIPs): `import zip from "…/<file>.zip?bytes"` yields a `Uint8Array` byte for byte (the `bytes-fixtures` plugin in `vitest.config.ts`); the stub then sends its `content-length`, as a real download does. See `tests/fixtures/sources/fis-points-lists/index.ts`.
3. Keep fixtures small: record one realistic page, not a whole season. Record by hand from a public endpoint only; never in CI; never from Olympedia, Olympics.com or Totallympics.
4. When a source changes format, record a new fixture next to the old one; the old one stays as a regression case.
5. A payload too big to keep whole (e.g. Team Belgium's 1 MB sitemaps) may be trimmed by hand after recording; say so in a `trimmedByHand` field of its `.meta.json`. A source whose test needs many files gets an `index.ts` next to them exporting the ready-to-stub list (see `tests/fixtures/sources/team-belgium/index.ts`).


## Sport names

Set by the #20 review. **One vocabulary:** `SPORTS` in `app/domain/sports.ts`, the Olympic programme's sports at discipline level as the IOC lists them for LA 2028 and French Alps 2030 (plus Breaking and Nordic combined for the reference Games): "Swimming", "Diving", "Artistic swimming", "Marathon swimming", "Water polo" (never "Aquatics"); "Cycling road", "Cycling track", "Cycling mountain bike", "Cycling BMX racing", "Cycling BMX freestyle" (never "Cycling"); "Equestrian dressage/eventing/jumping"; "Short track speed skating"; and so on. Each carries its Olympic cycle.

- **Store canonical names only.** `requireSport(raw)` (throws) in the row writer for every competition, result, Team and ranking an adapter hands over; `typedSport(raw)` (`app/curate/sport-field.tsx`, a 400 for anything else, with a `<SportOptions />` datalist) for every owner form that takes a sport. `canonicalSport(raw)` maps the names sources and people use ("Athletics (Track & Field)", "Short track", "Road cycling", "Open water swimming", "Softball") through one alias table, and is null for anything that is no sport ("Aquatics", "Cycling", "Olympic Games"). The owner's Games rows keep the Games' own label ("Olympic Games") as their sport; results on them carry `result.sport`.
- **Compare with `sameSport(a, b)`**, never `===` or `toLowerCase()`.
- **`olympicCycleOf(sport)`** is null for a name that is no sport: such an Entry has no Olympics target, rather than defaulting to summer.
- **A source that spans several sports sets the sport per competition or result from its discipline.** World Aquatics: one competition row per Olympic sport held there (source ref `<id>/<code>`, SW/DV/SY/OW/WP; high diving left out), and its timetable source splits the schedule by `SportCode`. UCI: each DataRide discipline is its own sport. A Source row's `sport` is the sport its pastes belong to (null when it spans several).
- Migration `0025_sport_vocabulary` rewrote stored names (and Team keys, which start with the sport).

## Sources and adapters

Set by the first Automatic source, ISU speed skating (#23). Every later Automatic source (#42, #43, #44) follows it.

**Source rows are data.** The `source` table holds each source's `key`, `tier` (`automatic` / `assisted` / `manual`), `cadenceDays` and health columns (`lastAttemptAt`, `lastSuccessAt`, `lastChangeAt`, `lastFailureAt`, `lastError`, `blockedAt`, `blockedReason`). Add a source with an `INSERT` appended to the migration that ships its adapter (see `db/migrations/0003_sources_and_results.sql`); change cadence or tier with an `UPDATE`, never a deploy. The domain rule `sourceHealth(source, now)` decides `due` (cadence elapsed, 2 h slack for cron jitter), `stale` (more than twice the cadence since the last success, or since `addedAt`), `blocked`, and the tier in effect (blocked → Assisted).

**The flow.** The daily cron calls `queueDueSources()`, which sends one `{ kind: "fetch-source", source }` job per due Automatic source. The queue consumer (one message per invocation, `max_retries` 3) calls `runSource(env, key)`, which:
1. stamps `lastAttemptAt`;
2. calls the adapter with a `SourceRun`;
3. on success stamps `lastSuccessAt`, and `lastChangeAt` when any row was inserted or changed;
4. on `SourceBlocked` (401, 403, 451 or a Cloudflare bot challenge) sets `blockedAt` / `blockedReason` and acks: a refusal is never retried, the source is Assisted until the owner retries it ("Fetch now" or "Retry fetch now" in the Run sheet's Source health step, `/curate/run/source-health`, clears the block);
5. on any other error stamps `lastFailureAt` / `lastError` and rethrows, so the job is retried.

**The adapter seam** (`app/ingest/source-adapter.ts`). An adapter is `{ run(run: SourceRun) }` and knows only its source's URLs and payloads:
- `run.now`, and `run.since` (start of the last successful run, null on the first): fetch only what changed since; on the first run choose a bounded backfill (ISU: one year).
- `run.fetch(url)` fetches politely, keeps the body as received in R2 and a `raw_copy` row, and returns `{ text, rawCopyId }`. Never call `fetch()` directly.
- `run.fetchStream(url)` is its sibling for large or binary payloads (FIS ZIPs): the body streams into R2 and comes back as a stream read from R2 (`{ body, rawCopyId }`), so a job never holds it whole (128 MB). `app/ingest/zip-stream.ts` reads a ZIP from such a stream entry by entry, line by line.
- A source that needs a credential (World Triathlon's API key) reads it with `run.secret(name)` and sends it as a header: `run.fetch(url, { headers: { apikey } })`. Never put it in the URL, which is kept with the raw copy. Without the credential the adapter throws `SourceBlocked` before fetching, so the source shows as blocked (Assisted) until the owner sets the Worker secret (`wrangler secret put <NAME> --env test|live`; `.dev.vars` locally). Tests pass it as `deliverIngestJobs(jobs, { NAME: "test-key" })`.
- A source whose endpoints only answer form POSTs (UCI DataRide) uses `run.fetch(url, { form })`: a url-encoded POST, fields in the given order. The form is kept with the raw copy as `<r2Key>.request` in R2 (the copy's metadata carries `method` and `requestKey`). Record such fixtures with `npm run record-fixture -- <source> <file> <url> --form "<url-encoded form>"` (exactly as the adapter encodes it, `URLSearchParams`); the meta then holds `requestBody`, and `stubOutboundFetch` matches on URL and body.
- When the API has no real payload to record (no credential yet), build fixtures by hand from its documented response examples, use made-up names and IDs, and say so in a `builtFromDocumentation` field of each `.meta.json`. Replace them with a recorded run once the credential exists.
- `run.rows` takes what was parsed: `competition()` (returns its id; only qualification-relevant senior competitions), `result()` (one Belgian performance; leave out DNS and withdrawals), `teamResult()` (one Belgian Team's performance with the `roster` the result credits; pass `teamEvent` when the result's event title is more specific than the Team's, e.g. ISU Division B), `team()` (finds or creates the Team a ranking row belongs to: a pair's members, or none for a nation ranking), `ranking()` (one Belgian ranking row, see "Rankings") and `entrants()` (a competition's entry list, replaced as a whole). Each input carries the `rawCopyId` it was parsed from, so every row links to its raw copy. A `sourceRef` (the source's own ID) makes a re-fetch update the same row instead of duplicating it.
- The writer keeps Belgian rows only (`person.nationality === "BEL"`), but filter early anyway. It matches identities with `identityMatch` (IF ID, then name + date of birth), remembers the IF ID on a name + date-of-birth match, moves "Athlete since" back for an earlier performance, and sends anything unmatched to the merge queue with its results attached.
- Adapters never touch D1, R2, identity rules or health.

**Merge queue.** An unmatched person becomes one `merge_queue_item` per IF ID (`scheme` + `value`); their results wait on it (`result.mergeQueueItemId`). `resolveMergeQueueItem(d1, itemId, resolution)` in `app/ingest/merge-queue.ts` links them to an Athlete, creates a new Athlete (from the item, "Athlete since" from its earliest result) or marks them "not an Athlete"; later runs then match on the IF ID, or keep attaching to the not-an-Athlete item. The Run sheet's Merge queue step (`/curate/run/merge-queue`) is the owner's page for it.

**Results, Teams and Upcoming.** A `result` belongs to an Entry (ADR 0001): an Athlete (or a merge-queue item), or a `team` (#27), and names its event as text. The domain rule `teamIdentity` decides which Team: by default one per Belgium + sport + event, whatever its roster; one per partnership (keyed on the members' IF IDs) in beach volleyball, rowing, doubles, pairs, duets, synchro, K2/C2 and the like. A Team's `roster_member` rows (Team × competition × Athlete or merge-queue item) are whoever the official result or squad list credits, kept as a union over the competition's results; resolving a merge-queue item moves its roster places to the Athlete. The Athlete page lists a Team result for every competition whose roster credits the Athlete, linked to the Team page (`/teams/:teamId`). Medals count through `belgiumMedals` (once per Entry per event) and `athleteMedals` (once per roster member), at Championships and the Games only. An `entrant` is an Athlete named on a competition's entry list; the Athlete page lists those competitions that have not ended yet under Upcoming.

**Assisted sources and the paste importer** (#25). An Assisted source is a `source` row with tier `assisted` (or any blocked source) plus its `sport` and `idScheme` (the IF ID scheme of its tables; the key when null); it needs no adapter. The Run sheet's Paste imports step (`app/curate/paste-imports.tsx`) lists those whose cadence has come round since `lastPastedAt` (`pasteImportDue`). "Read" keeps the pasted text (or the fetched plain HTML page) as a raw copy; the table is parsed by the pure rules in `app/domain/paste-table.ts` (`readPastedTable`, `readHtmlTable`, `columnMapping`, `belgianPastedRows`); "confirm" writes the ticked rows through `belgianRows()`, like an adapter, and saves `columnMapping` (role per lower-cased header) on the source. Rows need an IF ID column. Rankings (roles `ranking-position` / `ranking-points`, see "Rankings and the Qualification review"), timetables and heat detail extend the column roles and the confirm step rather than adding importers: `columnMapping(head, saved, guess)` takes the table kind's own guess, as timetables do (`timetableColumnMapping`).

**Manual results** (#26, `app/curate/manual-results.tsx`). A result is due when an Athlete is an `entrant` of a competition whose Source has tier `manual` and whose `endDate` has come (Belgian date), and they have no result there yet. The form keeps what the owner typed as a JSON raw copy whose `url` is the source URL (the PDF), then writes through the same `belgianRows(...).result()` writer, passing `athleteId` instead of `person` (no identity matching). DNS is recorded only here and never moves "Athlete since"; "Did not compete" writes no result and removes the `entrant` row.

**Participation** (set by #29). Confirmed and likely Participations from sources are **derived, never stored**: `participationsBetween(db, from, to)` (`app/calendar/participations.ts`) gathers the facts and the domain rule `participation(facts)` decides. Confirmed = an `entrant` row, a Selected `entry` (#34) or a `result` row names a Belgian Athlete or Team (start lists add their rows to the same "named" fact when they arrive, not a new table). Likely = a Belgian result at the previous edition, i.e. the latest earlier `competition` with the same `series`. So **every adapter sets `series`** on `run.rows.competition()`: a key stable from one edition to the next, prefixed by source (`isu:world-cup:calgary`, `isu:european-championships`, `olympic-games`); Europeans and Worlds, indoor and outdoor, short and long course get separate series. The pure rule `seriesKey({ source, name, kind, sport, city })` (`app/domain/series.ts`, with `seriesSlug`) is the default: years, seasons and edition ordinals dropped, a Championship without its host city, a circuit leg with its city (added when the name lacks it), the Games `olympic-games` / `olympic-winter-games` by the sport's cycle. Adapters sharpen it where the source gives more: ISU by venue city; FIS `fis:<sector>:<category>[:<venue>]` (`fis:al:wc:soelden`, `fis:al:wsc`); UCI `uci-cycling:<discipline id>:world-championships` for the Worlds, a World Cup leg without its round number and with its host country; World Archery without the stage number and without a city (its results rows carry none, and every writer of a competition must agree); VIS cuts a Championship's host after " - ". A timetable source computes the same series as its results source through the shared `competitionInput`. The paste importer takes an optional "Series (previous edition)" and otherwise derives it with `seriesKey`; the owner's Games rows carry the tracked Games' series. Tests: `tests/domain/series.test.ts`, `tests/worker/competition-series.test.ts` (one recorded run per source). The owner's word (added by hand, confirmed, kept, dropped, last checked) is the only stored part: `participation_curation`, written by the Run sheet's Selections & likely step (`app/curate/selections-likely.tsx`). "In contention" = an Active Belgian Entry at that competition has a Qualification status still in the race (`inContentionAt`, see "Qualification"). Calendar, iCal feed (#30), this step and the Paste imports step (a due Assisted source is listed only with a confirmed or likely competition within 7 days of today, from that source or in its sport) all read through `participationsBetween`.

**Adding an Automatic source:** record fixtures of one realistic run (trim by hand where large, note it in `trimmedByHand`), export the ready-to-stub list from `tests/fixtures/sources/<source>/index.ts`, write the Worker test against `deliverIngestJobs([{ kind: "fetch-source", source }])`, then the adapter, its registry entry and the Source row. Before it counts as Automatic, the owner runs "Fetch now" on the deployed test copy; a refusal shows it as blocked (Assisted).

## Active (Athletes and Teams)

Set by #28. Whether an Athlete or Team is **Active** is **derived, never stored**: `activeStatuses(db, now, only?)` (`app/roster/active.ts`) gathers the facts and the domain rule `activeStatus(entity, performances, facts, now)` (`app/domain/active.ts`; `isActive` for the boolean) decides, with the reason (`recent-performance`, `hold`, `no-recent-performance`, `retired`, `dissolved`, `nationality-change`).

- **Performances:** an Athlete's own `result` rows, the results of every Team whose roster credits them at that competition, and `athlete.profileLatestPerformanceOn` (the latest senior result on their Team Belgium profile, written by the roster seed, so seeded Athletes without a result in 12 months start inactive). A Team counts its own results only. DNS never counts.
- **Curated facts:** `active_fact`, one row per kind per Entry: `hold` (keep Active until `date`, `note` the reason), `retirement` (Athlete) / `dissolution` (Team) (inactive from `date` until a later performance), `nationality-change` (Athlete; inactive until the row is deleted; `note` the new nationality). Each has `source` and `checkedOn`. The owner edits them outside the Run sheet at `/curate/athletes/:id/status` and `/curate/teams/:id/status` (`app/routes/curate.entry-status.tsx`), linked from each Athlete and Team page.
- **Who reads it:** the default Athletes list (Active only; a search shows everyone, inactive marked), the Athlete and Team pages (status line from `app/roster/status-line.tsx`), and likely Participation (`participationsBetween` counts a previous edition only for a currently Active Entry). Qualification (#32) filters through it (see "Qualification"), and so should any later "follow only Active Entries" feature.

## Phases (Championship and Games pages)

Set by #31. Every Championship and the Games (and, from #35, each Games sport) is in one of five Phases: Standards → Qualification → Selection → Live → After.

**The rule is pure.** `currentPhase(inputs, now)` in `app/domain/phase.ts` decides from `PhaseInputs`: `startDate`/`endDate` (venue-local days), `venueZone` (Belgian time when null), `standardsPublishedOn`, `firstSelectedOn` (Belgian dates) and `firstSessionStart` (venue-local `YYYY-MM-DDTHH:mm`). Later inputs win (a competition that has started is Live even with no standards recorded); without a Session, Live starts at midnight venue time on day one; After starts when the last day ends at the venue. `phaseToShow(asked, current)` keeps `?phase=` to the current phase or an earlier one. Table tests: `tests/domain/phase.test.ts`; add a row for every new case.

**Inputs come from one place.** `phaseInputsFor(db, competitions)` (`app/competition/phase-inputs.ts`) builds the inputs for a batch of competitions; `currentPhasesOf(db, ids, now)` gives lists their phases. Today it fills the standards from the owner's record on `competition` (`standards_expected_on`, `standards_published_on`, `standards_url`, `standards_text`, edited at `/curate/championships/:id/standards`); `firstSessionStart` is the earliest timed `session.starts_at` (#37); `firstSelectedOn` is the earliest Selection's announced date of a Selected Entry (`firstSelectedOn` in `app/qualification/selection.ts`, #34; per sport at the Games). Pages never compute inputs themselves.

**Phase content plugs into panels.** `app/competition/phase-panels.tsx`: `loadPhasePanel(db, competition, phase, now)` loads only the shown phase (one member of the `PhasePanelData` union) and `PhasePanel` renders it inside `<section class="phase" aria-label="<Phase>">`. To add a phase's content (#32 Qualification, #34 Selection, #37/#38 Live, #41 After): widen that phase's union member, load it in its `case`, render it in place of the "not recorded yet" line. `PhaseBar` (`app/competition/phase-bar.tsx`) is the shared five-step bar (current marked "● now"; it and earlier phases are links, later ones greyed).

**The Games (#35)** reuse all three (`app/routes/games.tsx`: `/games` opens the next Games, `/games/:id` a given one). The Games followed are data in `TRACKED_GAMES` (`app/domain/games.ts`); a recorded Games is a `competition` of kind `games`, source `owner`, `sourceRef` its key, created when the owner saves its dates in the Run sheet's Schedules step (`app/curate/schedules.tsx`, the typed dates kept as a JSON raw copy). Each sport's first and last day is a `games_sport_window` row (inside the Games dates; source URL + checked date). `gamesPhaseInputs(db, games)` gives one `PhaseInputs` per sport (that sport's days, first Session grouped by `session.sport`, and first Selection grouped by `entry.sport`) and the whole, `combinedPhaseInputs([own, ...sports])` (Live at the first day or Session in any sport, After when the last ends). Chosen chips (`?sport=A,B`, `chosenSports` / `toggledSports`) combine their sports' inputs the same way, so one chip opens on that sport's phase. Sport chips are the extra `SportChips` argument to `loadPhasePanel` (`{ sports, chosen }`, none chosen = All sports): filter each phase's rows by `chosen` (Entries by sport; the medal table to Belgium's medals in those sports). Today they filter the standards: a standards line headed `<Sport>:` shows only under that sport's chip. The Games' standards are edited at `/curate/games/:id/standards` (same route module as Championships).

**Sessions, Entries and the Live day view** (#37). The owner pastes a timetable version in the Run sheet's Schedules step (`app/curate/timetables.tsx`, any Championship or Games not over yet): "Read" keeps the paste (or a plain HTML page) as a raw copy (source `timetable`); the pure rules in `app/domain/timetable.ts` read it with the paste importer's table readers and its timetable column roles (`date`, `start`, `end`, `session`, `sport`, `event`, `round`; a `round` cell without an `event` column is split by `splitEventRound`, LA28's "A / B" session descriptions into several rounds). The review names the Belgian **Entries** per event (`entry`: competition × sport × event × Athlete or Team, with `firstRound` after a bye; candidates are Athletes of that sport, the competition's entrants and the Entries already named). "Store" adds a `timetable_version` (stamp, published date, source URL, column mapping reused next time) and replaces the competition's `session` rows (venue-local `starts_at`/`ends_at` + IANA `venue_zone`; a coded Session holds several `session_round` rows, otherwise one row = one Session), keeping only rounds of events with an Entry. Games sport names are matched to the curated sport windows ("Athletics (Track & Field)" → "Athletics"). The Live panel (`app/competition/live-panel.tsx`) places each Entry with `roundsFor` (rounds from its first round; later ones `if-through`, pool/preliminary rounds `match-tbd`), `liveDays` / `dayToShow` for the day picker (`?day=`, venue-local; default today at the venue) and `toDisplayTime` for "03:30 · 18:30 LA". **#38** moves rounds on from results and adds heat detail and the medal table there; **#34** extends `entry` with its Selection status.

**Automatic Championship timetables** (#39). Adapters hand a Championship's whole timetable to `run.rows.timetable({ competitionId, version, publishedOn, sourceUrl, venueZone, rounds, rawCopyId })` (every round, Belgian or not; venue-local `date`/`start`; an empty list = not published yet, ignored). The writer keeps it as a tab-separated table (`timetableText`, raw copy source `timetable`, R2 metadata `derivedFrom` = the fetched copy) and fingerprints it (`timetable_version.fingerprint`, SHA-256 of that text; pasted versions get one too): a new fingerprint adds a version stamped `fetched YYYY-MM-DD` (unless the source has its own stamp); the latest version's fingerprint only re-places Sessions (Entries named since); a fingerprint seen on an older version is ignored, so the owner's later paste stands until the source changes. Sessions are built by `app/ingest/timetable-versions.ts` (`replaceSessions`, shared with the paste's Store) from `belgianRounds`: rounds whose event is `sameEvent` as an Entry's (case, "Metres"/"m", gender-word order and thousands separators ignored), renamed to the Entry's event. The owner names Entries on a fetched version with the Schedules step's **Name Entries** link (it reopens the review on the stored version's table; storing it keeps that version). Sources: ISU inside the #23 adapter (`events/{id}/schedule/` of each Championship not over); World Athletics, World Aquatics and World Archery as their own Source rows (`world-athletics-timetables`, `world-aquatics-timetables`, `world-archery-timetables`; daily; the next 400 days of Championships) whose adapters set `writesAs` to the results source, so their competitions are the results source's rows. Zones come from the source, else `venueZoneOf(IOC country, city)` (`app/domain/venue-zone.ts`; add hosts there), else the stated UTC offset as an `Etc/GMT±n` zone. A source that knows no zone passes `venueZone: null` to `competition()`, which then keeps the stored one. World Archery's SCHEDULE answered empty everywhere when #39 was built: its non-empty fixture is built from the API documentation.

**Results in the day view, and the Live day pass** (#38). `loadPlacedRounds(db, competition, chosen)` (`app/competition/placed-rounds.ts`) is the one place that places Entries: it feeds `roundsFor` the Entry's `entry_round` rows (per Entry × round name, so they outlive timetable versions: `outcome` advanced/eliminated, optional `heat`/`lane`/`opponent`/`startsAt`, `detailCheckedAt`) and its `result` in the event (same competition, same Athlete or Team, event name equal ignoring case). A round becomes live once the previous one says "advanced", a start list (any detail) names the Entry, or a finished result is dated on or after it; rounds drop after an "eliminated" round and after the date of a final result. Any detail field may be missing. The Live panel also shows the medal table (`loadMedalTable`): the other nations as the owner last pasted them (`medal_standing`, replaced per paste, raw copy source `medal-table`) and Belgium's row from `belgiumMedals` over the competition's results (pure rules `readMedalTable` / `medalTable`, `app/domain/medal-table.ts`); with Games chips chosen, only Belgium's medals in those sports. The **Live day pass** is `/curate/live/<step>` (`app/routes/curate.live.tsx`, steps in `LIVE_DAY_PASS`, its own `live` session, the same `app/curate/pass.tsx` layout and plumbing as the weekly Run sheet), offered by a banner on the weekly Run sheet while `liveCompetitions(db, now)` (competitions with Entries whose phase is Live) is not empty. Its own steps are in `app/curate/live-pass.tsx`; Merge queue and Source health (`problemsOnly`) reuse the weekly ones. A final result or a placed elimination recorded there is written through `belgianRows(env, "owner", now).result()` (sourceRef `live/<entryId>`, `sport` set at the Games, JSON raw copy under the results page URL). An Automatic source's result for the same Entry is matched only when its event name equals the Entry's.

**Reference Games (#46)** are history only: Paris 2024 and Milano-Cortina 2026, data in `REFERENCE_GAMES` (`app/domain/games.ts`), read at `/reference/:key` (`app/routes/reference.tsx`), Belgian results per sport. They have **no Phases, Expectations or qualification**: `referenceGamesOf(competition)` says whether a `games` competition is one (the owner's row, source `owner` / `sourceRef` its key, or Olympic Games a source published on its days), and `/games/:id` redirects those to the reference page. Anything that looks for "the next Games" or attaches Expectations, qualification or Selections to a Games must skip them. The owner's row is created with its first result by `referenceGamesRow(env, games, now)` (`app/competition/reference-games.ts`), with series `olympic-games` / `olympic-winter-games`, so it is LA 2028's and French Alps 2030's previous edition. Results come in by hand (`/curate/reference/:key`, JSON raw copy whose URL is the page read, e.g. Olympedia by hand) or through the paste importer's "Reference Games" choice. That row spans every sport, so its results carry `result.sport` (null elsewhere: the competition's sport). A Team result by hand names the Team and the Athletes it credits (`result()` with `teamId` + `roster`, no identity matching); the page links every Athlete and Team, inactive ones included.

## Qualification (status, tracks and targets)

Set by #32; the hub for #33 (Rankings and Qualification review), #34 (Selection) and #36 (Quota places). Vocabulary: GLOSSARY "Qualification status", "Qualification track", "Quota place"; ADR 0002.

**Where it is stored.** A potential Entry for a target is an `entry` row (competition × sport × event × Athlete **or** Team, the same table the timetable step names Entries in; never a parallel table). Its status lives on it: `qualification_status` (`QualificationStatus`: `not-in-contention` · `at-risk` · `on-track` · `eligible` · `qualified` · `selected` · `not-selected` · `withdrawn`; null = none recorded), `qualification_source` and `qualification_checked_on` (Belgian date). Its tracks are `qualification_track` rows (`entry_id`, `position`, `name`, `needed`, `has`, `state` = `met` / `not-met` / `pending`, `better` = `higher` / `lower` / null, `source`, `checked_on`, and `changed_on`, which moves only when needed / has / state change). The window's closing date is `competition.qualification_closes_on`, edited with the standards (`/curate/{championships,games}/:id/standards`). A status is set on the Athlete or Team only: an Athlete cannot get an Entry in an event where a Team whose roster credits them competes.

**Pure rules** (`app/domain/qualification.ts`, tests `tests/domain/qualification.test.ts`): `qualificationTargets({ sport, competitions, withEntries }, now)` picks the next Olympics (the next Games of the sport's cycle, `olympicCycleOf`; reference Games skipped via `referenceGamesOf`) and the next Championship (the earliest not over with an Entry recorded, else the earliest in the sport; only that one); `trackProgress(track)` fills a progress bar (met = 100; else the figures in needed / has: ranks "top 24" / "#31" / "28th" and h:mm:ss times are lower-is-better, anything else uses `better`, default higher); `windowCountdown(closesOn, now)`; `inContention(status)`.

**Reading** goes through `app/qualification/entries.ts`, which filters every Entry through `activeStatuses` (only Active Entries have statuses and tracks): `potentialEntries(db, competitionIds, now, who?)` (the Qualification phase panel, the owner's page), `qualificationOf(db, { athleteId | teamId, sport }, now)` (the Athlete and Team pages' Qualification section, `app/qualification/qualification-section.tsx`, `?target=championship` for the second target), `inContentionAt(db, ids, now)` (likely Participation).

**Writing** is the owner's page `/curate/{championships,games}/:id/qualification` (`app/routes/curate.qualification.tsx`; intents `add-entry`, `set-status`, `save-track`, `remove-track`; reference Games 404). Saving a status stamps it checked today.

**Extension points.**
- **#33 (Rankings, Qualification review):** done, see "Rankings and the Qualification review".
- **Selection (#34, built):** Selected / Not selected are statuses on the same `entry` row, with the Selection behind them in `selector` (national federation for a Championship, `BOIC` for the Games: `selectorFor`), `selection_source` (URL), `selection_kind` (`press-release` / `entry-list`), `selected_on` (announced, Belgian date) and `selection_raw_copy_id`. Storage in `app/qualification/selection.ts` (`selectionCandidates`, `recordSelection`, `applyEntryList`, `firstSelectedOn`); pure rules in `app/domain/selection.ts` (`namesFoundIn`, `selectionDue`, `entryListSelection`). The owner enters one per competition × sport in the Run sheet's Selections & likely step (`app/curate/selections.tsx`; "Find names" keeps the pasted press release as a raw copy, source `selection`, and pre-ticks the names found; "Save" makes the ticked candidates Selected and the other Active, non-withdrawn candidates Not selected). It is due when the competition starts within 8 weeks or its window has closed; any other opens from the owner's Qualification page (`?selection=<id>&sport=<sport>`). An adapter's `run.rows.entrants()` replaces the Selection with the IF entry list (Athlete Entries only; a list without Belgians is ignored, as it may not be published yet). A place passing to a new partnership = old Team's Entry `not-selected`, new Team's Entry `selected` (both candidates in the same Selection). The Selection phase panel lists Selected Entries, then Not selected, then those still qualifying. Selected Entries count in the "named" fact (confirmed Participation). At the Games, a saved Selection or entry list calls `linkAtSelection` (#36) for each event it touched, so NOC-owned places follow it. Each Selected Entry shows its latest Seed and the owner's pick next to it (#40, see "Expectations").
- **#36 (Quota places):** a separate `quota_place` table (ADR 0002), never a status. A named place links to its `entry` when earned; an NOC-owned place links at Selection. Show it on the Games' Qualification panel next to (not instead of) the Entries' statuses: widen the `qualification` member of `PhasePanelData`. A quota-place track on an Entry stays a plain `qualification_track` (e.g. "Quota place · 1 of 24 · not allocated yet").

**Quota places (#36).** `quota_place` rows (`competition_id` = a Games, `sport`, `event` matching its Entries' event, `number` within the event, `kind` = `noc` / `named`, `state`, `reallocated`, `earned_via`, `entry_id`, `source`, `checked_on`). Championships have none (the intents refuse, the panel shows no section). Pure rules in `app/domain/quota-places.ts`: `quotaPlaceTransition(place | null, event)` is the only way a state changes (`hold` → Provisional, `allocate` / `reallocate` → Allocated for a new place; then `allocate`, `accept`, `enter` (needs a linked Entry), `decline`, `lose`; Entered / Declined / Lost are final); `quotaPlaceLinkable(kind, status)` (named: always; NOC-owned: only a Selected Entry). Storage in `app/qualification/quota-places.ts`: `quotaPlacesOf(db, gamesId)` (panel and owner's page), `recordQuotaPlaces(db, { …, how, count })` (the owner's n new places by hand), `holdEarnedPlaces` (a nation ranking's places, adjusted to its count; see "Rankings and the Qualification review"), `linkAtSelection(db, gamesId, sport, event)`: NOC-owned places in play follow Selection in their event (leave an Entry no longer Selected, go to Selected Entries without one), called after every status write on the owner's page. **#34:** call `linkAtSelection` wherever Selection writes a status. Owner intents on `/curate/games/:id/qualification`: `add-quota-places`, `move-quota-place` (needs a source; stamps checked today), `link-quota-place`, `remove-quota-place`.

## Rankings and the Qualification review

Set by #33. **A ranking snapshot** (`ranking_snapshot`) is where one Belgian Athlete or Team stood on one ranking list on one day: `source`, `ranking` (the list's name, stable across seasons: "ISU World Cup 1500m Men", "FIS points list · Giant slalom Men", "World Archery world ranking · Recurve Men Team", "Official World Golf Ranking"), `sport`, `position`, `points` (as published), `as_of` (the list's date, else the run's Belgian date), raw copy. Adapters write them with `run.rows.ranking({ ranking, sport, asOf, position, points, rawCopyId, person | teamId })`: one row per ranking × Entry × day (a re-fetch updates it). A person must match an Athlete (IF ID, then name + date of birth, which remembers the IF ID); **rankings never create Athletes or merge-queue items**. Pair rankings go to `run.rows.team({ members })` (the partnership), nation rankings to `run.rows.team({ members: null })` (the default Team in the event, the same Team its results go to). Sources so far: ISU World Cup standings (fetched when a World Cup competition became official), FIS points lists (the ZIP's `pts` file, 999.99 = no points), World Archery world rankings (weekly, first run after Monday noon UTC), OWGR golf (ranking-only source `owgr-golf`, weekly), the UCI road World Ranking (inside `uci-cycling`, weekly, first run after Tuesday noon UTC: Men and Women Elite, Belgian riders and Belgium's nation position on its default Team in "Road race Men/Women Elite"), and World Triathlon's world and Olympic qualification rankings (inside `world-triathlon`, weekly; built from the documented shapes, blocked without the key). **Pasted rankings:** the paste importer's `ranking-position` / `ranking-points` column roles make a pasted table a ranking (`belgianRankingRows`); confirming with the ranking's name, its date and the sport stores each known Belgian's position through `belgianRows().ranking` (without a name column: Belgium's default Team in the named event), so Assisted sports' rankings need no new importer.

**Tracks follow rankings.** A `qualification_track` may name the ranking it follows (`ranking_source` + `ranking`; the owner picks it on `/curate/{championships,games}/:id/qualification` among the rankings the Entry has snapshots on, form value `<source>|<ranking>`). Every new snapshot (and linking a track) runs `followRanking` (`app/qualification/ranked-tracks.ts`): `has` becomes "#18 · 412 pts" and the state follows the pure rule `rankedTrack` (pending while the window is open; met / not met by the "Top N" in `needed` once `qualification_closes_on` has passed). `changed_on` (and `previous_has`, shown as "was → now") move only on a real change.

**`suggestStatus(entry, tracks, ranking, quotaPlaces)`** (`app/domain/qualification.ts`, table-tested): Selected / Not selected / Withdrawn stay; a named place linked to the Entry → Qualified (On track while Provisional); a met track (`meetsCriteria`) → Qualified at a Championship, at the Games compared with the event's NOC-owned places (candidates ≤ places → Qualified, On track while Provisional; more → Eligible; none recorded → On track); else the followed ranking's position against the "Top N" (`rankingPlaces`) → On track / At risk; every track missed → At risk; At risk becomes Not in contention once the window has closed; otherwise no suggestion (null).

**The Qualification review** (Run sheet step 5, `app/curate/qualification-review.tsx`) lists Active Entries of Championships and Games not over yet (reference Games skipped) with a track `changed_on` after `qualification_checked_on` (or never checked), or an unfollowed ranking in their sport whose latest snapshot (recorded after the check) moved. One table row each: what changed, current → suggested status, source and last check. Intents: `apply-suggestion` (writes the suggestion, source = the ranking and its date or the track's source, checked today), `keep-status` (only stamps checked today), `set-status` (`status` + `source`). At the Games each status write calls `linkAtSelection`. Nothing is written without one of these actions.

**Nation rankings hold Quota places** (story 80; #20 review). When a nation ranking (Belgium's default Team) gets a snapshot and a track of that Team's Entry at a Games (not a reference Games, not over) follows it, `followRanking` keeps the event's NOC-owned places at what the position earns: the pure rule `placesEarned(needed, position)` reads the track's needed text as the owner copied it from the qualification system ("Top 12 nations" = one place inside the Top 12; "Top 12 nations: 3 places"; bands "Top 4: 3 places · top 10: 2 places"; null when it names no Top N), and `quotaPlaceAdjustment` / `holdEarnedPlaces` (`app/qualification/quota-places.ts`) hold the missing places as Provisional (`earned_via` = the ranking, source = ranking · date) and remove only surplus Provisional, unlinked, non-reallocated places that ranking held. A re-fetch changes nothing. `recordQuotaPlaces` stays the owner's "add n places" by hand.

**Not built yet:** VIS beach and volleyball rankings. Evidence (#20 review, 14 Nov 2026): the documented `GetBeachOlympicSelectionRanking` (Gender, GamesYear 2028 or 2024) and `GetBeachWorldTourRanking` answer `<NotInNewFormat id="1008" />` or 400; the new `GetBeachRankingList` works (`Fields="No Type Gender Date"`, 5 611 rankings, e.g. No 7215 Type 6 Gender 0 dated 2026-11-09) but `GetBeachRanking No="7215"` returns only the header element whatever `Fields` or `<Relation Name="Entries|Ranking|Teams">` is asked, guessed entry requests (`GetBeachRankingEntryList`, `GetBeachRankingTeamList`, `GetBeachRankingEntries`) answer 400, and the VIS SDK documentation (fivb.org/VisSDK/VisWebService) no longer documents either request; the volleyball side documents only per-tournament player statistics (`GetVolleyPlayersRankingList`), no world ranking. Paste them through the importer's ranking roles until FIVB documents the new format. Also not built: UCI rankings of track, mountain bike and BMX (the same DataRide requests with their discipline id; group names not checked), World Triathlon nation rankings (rows without an athlete are not documented), and Quota places from rankings for partnerships (beach pairs).

## Expectations (Seeds, personal picks, Gracenote; Verdicts)

Set by #40. Vocabulary: GLOSSARY "Expectation", "Seed", "Verdict"; decided in #12 (snapshots) and #16 (picks). Expectations exist only at Championships and the Games (never reference Games, never on Athlete pages) and attach to an `entry` row.

**Storage** (`app/db/schema.ts`, migration `0023_expectations_and_picks`):
- `expectation_snapshot`: one dated external Expectation per Entry × `source` × `as_of` (a second one on the same date replaces the first): `source` (`seed`; #41 adds `gracenote`, `EXPECTATION_SOURCES`), `place_from` / `place_to` (a place when equal, else a range), `method` (Seeds only, `SEED_METHODS`: `world-rank` = the monthly world-ranking position before the entry list exists; `federation-seed` / `ranking` / `season-best` = the final Seed from the entry list, `isFinalSeed`), `as_of` (Belgian date the forecast was taken), `source_url`, optional `raw_copy_id`, `recorded_at`.
- `personal_pick`: one row per Entry (PK `entry_id`), no history: `shortcut` as typed back (`shortcutText`: `medal`, `QF exit`, `5-8`), `place_from` / `place_to` (`expandShortcut`), `picked_at`. Owner-only.

**Pure rules** (`app/domain/expectations.ts`, tests `tests/domain/expectations.test.ts`): `readShortcut(typed)` → `Shortcut | null` (Gold/Silver/Bronze, Medal, Final or Top 8, round exits SF 3–4 · QF 5–8 · R16 9–16 · R32 17–32 · R64 33–64, an exact place, a range), `expandShortcut`, `shortcutLabel`, `placeRangeLabel` ("5th–8th"), `pickLockAt(phaseInputs)` (first Session at the venue, else 00:00 venue time on day one; at the Games pass `gamesPhaseInputs(...).whole`, so every sport locks together), `canPick({ status, lockAt }, now)` (Selected and before the lock), `worldRankSnapshotDue(seeds, today)` (none this month and no final Seed), `lastSnapshotBefore(snapshots, day)` (the latest snapshot dated before `day`).

**Reading and writing** go through `app/expectations/expectations.ts`: `expectationsOf(db, entryIds, now)` (per Entry: `seeds` oldest first, latest `seed`, `worldRankDue`, `pick`), `pickLockFor(db, competition)`, `setPick` / `clearPick` (409 unless `canPick`; 400 for a typed value that is no shortcut), `recordSeed` / `removeSeed`, and `recordWorldRanks(db, ranks, now)`, which writes a `world-rank` Seed only when that month's is due.
- The owner's page is `/curate/{championships,games}/:id/expectations` (`app/routes/curate.expectations.tsx`; intents `pick`, `clear-pick`, `record-seed`, `remove-seed`), linked from the reader page's Selection phase for the owner. Picks per Selected Entry; Seeds per potential Entry still in the running, "World-rank snapshot due" when this month's is missing.
- The Selection phase panel shows each Selected Entry's latest Seed (method, date, and the monthly world ranks before a final Seed) and the pick, plus when picks lock.

**Monthly world-rank Seeds from rankings (#33):** the ranking a `qualification_track` follows is the Entry's world ranking. `followRanking` (`app/qualification/ranked-tracks.ts`, run after every ranking snapshot and when a track is linked) calls `recordWorldRanks` for each Entry whose competition starts after the snapshot's date: one `world-rank` Seed a month (the first list of the month), none once a final Seed exists. Entries without a followed ranking get their monthly Seed by hand ("World-rank snapshot due"). A final Seed derived from an entry list goes through `recordSeed` with method `ranking` or `season-best`.

**Verdicts and the After phase** (#41). Pure rules in `app/domain/verdicts.ts` (tests `tests/domain/verdicts.test.ts`): `verdict(expectation, { place, withdrawnBeforeLock })` → `beat` | `met` | `missed` | `voided` | null (no Expectation), `outcomeOf(results)` (the latest-dated result's place, best place on that date: a shared place counts as its best; none = Missed), `withdrawnBeforeLock(withdrawnAt, lockAt)`, `tally(verdicts)` (voided and null left out), `impliedCounts(ranges)` (a range counts only when wholly inside 1–3 / 1–8; Belgium's own counts are its places as one-place ranges).
- `loadAfter(db, competition, chosen)` (`app/expectations/verdicts.ts`) is the After panel's data: Entries Selected or Withdrawn (a Withdrawn one only when something was expected of it), filtered by the Games sport chips; per source (`seed`, `gracenote` at the Games, `pick`) the Expectation as it stood — snapshots via `lastSnapshotBefore(..., start)` where start is the competition's first day, at the Games the first day of the Entry's sport (`games_sport_window`, else the Games' first day) — and the pick as locked. The outcome is the Entry's results in its event (same Athlete or Team, event equal ignoring case). Voided: status `withdrawn` and `entry.withdrawn_at` before `pickLockFor` (it voids every source's Verdict for that Entry; for withdrawals recorded before #41, midnight of `qualification_checked_on` stands in). Implied counts leave voided Expectations out.
- **Withdrawal moment:** `entry.withdrawn_at` (ISO instant, migration `0024_verdicts`). Every writer of `qualification_status` spreads `withdrawalColumn(status, now, stated?)` (`app/qualification/withdrawal.ts`): Withdrawn keeps the first recorded moment unless the owner states one; any other status clears it. The owner's Qualification page takes an optional "Withdrawn at" (Belgian wall clock) on Save status.
- **Gracenote** (the Games only): `recordGracenote` / `removeGracenote` (an `expectation_snapshot` with `source` `gracenote`, `method` null, `source_url` required — the Sporza/VRT article), typed as a shortcut on the owner's expectations page (intents `record-gracenote`, `remove-gracenote`); read as `expectationsOf(...).gracenote`. After attributes each compared update ("Gracenote via sporza.be · date", linked).
- **BOIC target** (the Games only): `boic_target` (one per Games: `medals` and/or `top8`, `stated_on`, `source_url`), `boicTargetOf` / `setBoicTarget` / `clearBoicTarget`, intents `boic-target` / `clear-boic-target`. A delegation-level count, never an Expectation: shown in After's "Medals and top 8" only with All sports. Championships compare against the Seed- and pick-implied counts only.
- The After panel (`After` in `phase-panels.tsx`): "Expectations vs outcome" (raw places + Verdict per source, outcome), "Tally", "Medals and top 8", "Best results" (top 5 places), then the final medal table (`MedalTablePanel` with `title`). Nothing of this appears on Athlete pages.

## Offline reading and curation routes

The service worker caches every page and its React Router data (`<path>.data`) as it is viewed, network first, and precaches the app shell. **Curation routes must live under `/curate`** (`CURATION_PATH` in `app/domain/offline-reading.ts`): they are never cached, and offline the root layout replaces them with an offline message, so the owner never fills in a stale form. Anything else counts as a reader page.

**Curation is owner-only.** The fetch handler refuses every `/curate` path (and its `.data` request, in any case or encoding: `isCurationPath`) with a 403 unless the request comes from the owner (`isOwner` / `refuseNonOwnerCuration` in `app/owner.ts`, both async; reader loaders `await isOwner(...)` to offer curation links). On a deployed copy that means a **verified Cloudflare Access JWT**: the `Cf-Access-Jwt-Assertion` header must be an RS256 token signed by a key from `https://<ACCESS_TEAM_DOMAIN>/cdn-cgi/access/certs` (fetched with plain `fetch`, kept 10 minutes per isolate), with `ACCESS_AUD` among its `aud`, `iss` = `https://<ACCESS_TEAM_DOMAIN>`, not expired or not yet valid, and its `email` claim equal to `OWNER_EMAIL` (case ignored). The bare `Cf-Access-Authenticated-User-Email` header is never trusted there. Deployed copies fail closed: no or bad JWT, an empty `ACCESS_TEAM_DOMAIN` / `ACCESS_AUD`, or certs that cannot be fetched → not the owner. `OWNER_EMAIL`, `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD` are vars per environment in `wrangler.jsonc`. The local dev copy (`APP_ENV` "dev") has no Access in front: there the email header is taken as sent and a request without it counts as the owner's. In tests, `signedInAs(email)` from `tests/support/worker.ts` sends the email header (enough in dev); `getDeployed(path, init, { vars, certs })` runs a request as the deployed test copy would, stubs the certs endpoint with the test key (`tests/support/access.ts`: `accessCerts`, `accessJwt(claims, { signedBy })`) and adds a valid Access JWT for a `signedInAs` email unless the request brings its own `Cf-Access-Jwt-Assertion`. Static files are served as named (`assets.html_handling: "none"`). The service worker is registered in production builds only.

## The Run sheet (curation workspace)

Set by #24. The weekly session is `/curate/run/<step>` (`app/routes/curate.run.tsx`); `/curate` opens its first step. The steps, their order, time estimates, per-item minutes and one-line purposes are data in `WEEKLY_RUN_SHEET` (`app/domain/run-sheet.ts`); `runSheetProgress` decides ✓ (empty or passed) and the estimated time left.

**Adding a step's items** (#25, #26, …): put the step's loader, action and component in `app/curate/<step>.tsx` (see `source-health.tsx`, `merge-queue.tsx`): `load…(db, now)` returns the items plus `open` (the item count), `actOn…(…)` does one owner action and returns the session-log message. Then in the pass's route (`curate.run.tsx`, or `curate.live.tsx` for the Live day pass) add the open count to `loadSteps`, dispatch the step's intents in the `act` callback it hands to `passAction`, and render the component as a child of `PassLayout`. **Both passes share `app/curate/pass.tsx`:** a `PassDefinition` (session `sheet`, `steps` from `WEEKLY_RUN_SHEET` / `LIVE_DAY_PASS`, `path`, rail title, "next week" / "tomorrow", finish label), `stepIndex` (404 for an unknown step), `loadPassFrame` (progress, Live competitions, session log), `passAction` (the "next" and logging plumbing) and `PassLayout` (rail, step with Back / Next, time left, session log); a route only declares its steps' loaders, intents and components. Every action is logged through `logAction` (`app/curate/session.ts`); "next" with items left logs a pass, which ticks the step for the rest of the session. A session opens with its first logged action and closes on "Finish session" (the last step's Next).

## Cron triggers

The scheduled handler dispatches on `controller.cron`: `0 4 * * *` daily ingest (queues due sources), `0 3 * * 1` weekly backup (`runScheduled(cron, time)` in tests). Both run on the live copy only; the test copy has none.

## Environments and deploying

`wrangler.jsonc`: top level = local dev and tests; `env.test` and `env.live` = the two deployed copies, each with its own D1 (`bsh-test`, `bsh-live`), R2 bucket and queue. `workers_dev` and preview URLs are off; each copy has a custom-domain route. The test copy has no cron triggers; the live copy runs the daily ingest cron.

- **Test copy:** `.github/workflows/deploy-test.yml` runs typecheck, tests, then `npm run deploy:test` on every push to `main`.
- **Live copy ("update app"):** `.github/workflows/deploy-live.yml`, run by hand (`gh workflow run deploy-live.yml --ref main`).
- Pull requests run `.github/workflows/ci.yml` (typecheck + tests).

With the Cloudflare Vite plugin, the environment is chosen at **build** time (`CLOUDFLARE_ENV=test react-router build`); `wrangler deploy` then uses `build/server/wrangler.json`. Commands that must read the source config (D1 migrations, `wrangler types`) pass `-c wrangler.jsonc`.

Placeholders in `wrangler.jsonc` (marked `PLACEHOLDER`) must be replaced before the first deploy: the custom domain (`bsh.example.com`, `test.bsh.example.com`), the D1 database ids, and the Access team domain and AUD tags (`ACCESS_TEAM_DOMAIN`, `ACCESS_AUD`).

Cloudflare Access is configured in the Zero Trust dashboard, not in code: one self-hosted application per copy covering the whole domain, an email allowlist policy with one-time PIN login, and a second self-hosted application for the iCal feed path only (`<domain>/ical/*`) with a single Bypass policy (Include: Everyone). A more specific path application takes precedence over the whole-domain one, so only the feed skips Access. **Human step per copy:** put the Zero Trust team domain (`<team>.cloudflareaccess.com`, Zero Trust → Settings → Custom pages / team domain) in `ACCESS_TEAM_DOMAIN` and that copy's whole-domain application's **Application Audience (AUD) tag** (Access → Applications → the application → Overview) in `ACCESS_AUD`, replacing the `REPLACE_WITH_*` placeholders in `wrangler.jsonc` (`env.test`, `env.live`). Until both are set, `/curate` answers 403 on that copy.

**iCal feed** (#30, `app/calendar/feed.ts`, `app/routes/ical.tsx`). Calendar apps can't pass Access, so the feed is `/ical/<token>.ics` and answers only when `<token>` equals the `ICAL_FEED_TOKEN` Worker secret (compared in constant time); anything else gets a bare 404, and without the secret the feed is off and the Calendar shows no subscribe link. Set it per copy with `wrangler secret put ICAL_FEED_TOKEN --env test|live` (a long random value, e.g. `openssl rand -base64 32 | tr '+/' '-_' | tr -d '='`; locally in `.dev.vars`); putting a new value cuts off every old subscription. The feed lists what the Calendar tab shows (through `participationsBetween` + `onCalendar`), from a year back to four years ahead, as all-day events; the iCal text itself is the pure rule `icalFeed` (`app/domain/ical.ts`). In tests, `getWithSecrets(path, { ICAL_FEED_TOKEN })` sets the secret for one request. The owner's Access email goes in `OWNER_EMAIL` (placeholder `owner@example.com` in `env.test` and `env.live`).
